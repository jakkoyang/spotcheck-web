# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

SpotCheck: a mobile-first web app showing real-time-ish "how busy is it" and vibe info for UW-Madison study spots (libraries, unions, etc.), centered on a Mapbox map. Full product spec lives in `spotcheck_PRD.md`; the working sprint checklist (kept in sync with actual repo state) is `spotcheck_TASKS.md`. Both are local planning docs, not app code.

## Commands

- `npm run dev` — start the Vite dev server
- `npm run build` — typecheck (`tsc -b`) then production build via Vite
- `npm run lint` — ESLint over the whole repo
- `npm run preview` — serve the production build locally

There is no test suite configured yet (no test script, no test runner installed).

Requires `VITE_MAPBOX_TOKEN` set in `.env` (see `.env.example`) for the map to render tiles locally. `VITE_SUPABASE_URL` / `VITE_SUPABASE_ANON_KEY` are reserved for Sprint 4 and currently unused by any code.

## Architecture

**Data-access seam is the core architectural rule.** All data reads go through `src/lib/data.ts` (`getLocations()`, `getVibeTags()`), which currently proxies to hardcoded arrays in `src/lib/mockData.ts`. Components and views must import only from `src/lib/data.ts`, never from `mockData.ts` directly. This is intentional: the plan (PRD §5) is to swap `data.ts`'s implementation to real Supabase queries in Sprint 4 with zero changes to any calling component. When adding a new data operation, add it to `data.ts` first, backed by mock data, even if Supabase doesn't exist yet.

**Types mirror the target Supabase schema.** `src/types/location.ts` defines `Location`, `VibeTag`, `AtmosphereScore` to match the Postgres schema described in PRD §8 (`locations`, `vibe_tags`, `location_tags`, `busy_reports` tables), so the eventual Supabase adapter is a mechanical mapping rather than a redesign. Keep this alignment when editing types.

**View structure:** the app is a single map-first screen, `src/views/ExploreView.tsx` (the earlier Home/Map/Search tabs were merged into it). The map is always visible; one search bar + category/vibe chips (`SearchBar`, `FilterBar`) sit on top and drive both the pins and a draggable `BottomSheet` (peek/half/full snaps, `src/lib/sheetSnaps.ts`) that shows either the filtered spot list or the selected spot's `LocationCard`. Filtering/sorting lives in `src/lib/spotFilters.ts`; address lookup in `src/lib/usePlaceSearch.ts`. `App.tsx` routes `/` to `ExploreView` and redirects everything else there — add new routes (e.g. Saved) alongside it.

`npm run dev:mock` (`.env.mock`) blanks the Supabase env vars so `data.ts` falls back to mock data even when `.env` points at a live project.

**Mobile app (`mobile/`):** an Expo/React Native port (Expo SDK 58, React Native 0.88) with its own `AGENTS.md`. It mirrors the web Explore screen in `mobile/src/app/index.tsx` (`@rnmapbox/maps` + `@gorhom/bottom-sheet`), and `mobile/src/lib/{mockData,spotFilters,usePlaceSearch}.ts` are copies of the web files — keep them in sync (the mobile `usePlaceSearch` additionally sends a User-Agent, which Nominatim requires and browsers can't set). `mobile/start-native-mock.cmd` sets `EXPO_PUBLIC_USE_MOCK_DATA=1` to serve mock data (spot data only — auth still uses Supabase). Android runs edge-to-edge, so the window never resizes for the keyboard; the Explore screen handles the keyboard itself rather than relying on the bottom sheet's keyboard modes.

Shared-with-web copies also include `openingHours.ts` (evaluator for the OSM `opening_hours` subset our data uses) and `freshness.ts`. Mobile-only features — busy reports, saved spots (AsyncStorage, via `data.ts`), clustering + category-icon pins (`SpotsLayer`), walking times/Nearest (`useUserLocation`, `distance.ts`), light/dark theme (`theme.ts`; NativeWind `dark:` classes plus `useThemeColors()` for native colors), haptics, and Google/Apple sign-in (`auth.ts`, Supabase OAuth via `expo-web-browser`) — are not yet ported to web. Live busy reports need `supabase/migrations/0002_busy_reports_and_hours.sql` applied (run it before re-running `seed.sql`, which now writes `opening_hours`).

The Mapbox logo and attribution must stay visible on the map (Mapbox ToS); they sit just under the filter chips. Local Android builds need **JDK 17** (e.g. Gradle's `~/.gradle/jdks/eclipse_adoptium-17…`): Android Studio's bundled JDK 25 makes the `react-native-worklets` CMake step fail. `android/` is generated (gitignored); `expo prebuild` wipes `local.properties`, so set `ANDROID_HOME` for Gradle rather than editing it.

**Performance (target: 4 GB / basic Android phones).** Judge smoothness on a release build (`npm run android:release` in `mobile/`), never the dev build, which is far slower. On the Explore screen, keep derived data memoized (`results`, `pinnedLocations`) and handlers stable (`onSelectSpot`, `renderSpotRow`): a new array makes `SpotsLayer` re-send every pin to Mapbox and re-cluster, and `SpotsLayer`/`LocationListItem` are `memo`ized so they skip re-renders. Map layer styles are module constants or memoized on the theme; `FlatList` separators are a module-level component; the location puck doesn't pulse (it forces continuous map redraws). Shadows use native `elevation` on Android (`elevation.ts`; blurred `boxShadow` redraws every frame) and `boxShadow` on iOS. Release builds use R8 + resource shrinking and ship `armeabi-v7a`, `arm64-v8a`, `x86_64` (`expo-build-properties` in `app.json`). R8 strips classes only loaded by name: the `extraProguardRules` keep for `expo.modules.adapters.react.apploader.**` is required, or the geofence task crashes whenever it fires while the app is closed. Test anything background-related on a release build (`run-as` doesn't work there; read `[check-ins]` lines in logcat instead).

**iOS builds** go through EAS (`mobile/eas.json`: `development`, `development-simulator`, `preview`, `production`); EAS picks the SDK 58 image (Xcode 27) automatically. The bundle ID and Android package are both `com.spotcheck.app`. `.env` is gitignored, so EAS cloud builds don't see it: the `EXPO_PUBLIC_*` values (Mapbox token, Supabase URL/anon key) must be set as EAS environment variables (`eas env:create`) for each environment the profiles name. No secret Mapbox download token is needed. On iOS, Apple sign-in is native (`expo-apple-authentication` → `supabase.auth.signInWithIdToken`), so the Supabase Apple provider must list the bundle ID as an authorized client ID; Android keeps the web OAuth flow.

**iOS 27 / UIScene.** Apps built with the iOS 27 SDK (Xcode 27) must use the UIKit scene life cycle or they won't launch ("UIScene life cycle is required…"). SDK 58's prebuild template provides it (`SceneDelegate.swift` subclassing `ExpoAppSceneDelegate`, plus `UIApplicationSceneManifest` in `Info.plist`), so there's nothing to configure; don't hand-edit `ios/`. Since SDK 58, stack headers on iOS 26+ are transparent (Liquid Glass) by default, so screens with a header and a root `ScrollView` (Settings, Check-in prompts) set `contentInsetAdjustmentBehavior="automatic"` to keep content below it.

**Mapbox versions are paired.** `@rnmapbox/maps` is pinned to an exact version in `package.json`, and `RNMapboxMapsVersion` in `app.json` pins the native Mapbox engine for both iOS and Android; they must match (use the engine version in the library's own `package.json` `mapbox` field). A mismatch fails the iOS build with Swift errors in `RNMBXStyle.swift` such as missing `lineBorderGradient`. Current pair: library 10.3.17, engine 11.33.0. Library versions before ~10.3.17 don't compile against React Native 0.88.

**Local iOS simulator builds** (Mac with Xcode 27): `npx expo run:ios` currently treats the iOS 27 simulator as a physical device and fails with "No code signing certificates are available". Build with `xcodebuild` instead, from `mobile/ios` after `npx expo prebuild --platform ios`: `xcodebuild -workspace SpotCheck.xcworkspace -scheme SpotCheck -configuration Release -sdk iphonesimulator -destination "id=<simulator UDID>" -derivedDataPath build/dd CODE_SIGNING_ALLOWED=NO build`, then `xcrun simctl install`/`launch` the `.app` from `build/dd/Build/Products/Release-iphonesimulator/`. Local builds read `mobile/.env` (gitignored): `EXPO_PUBLIC_MAPBOX_TOKEN` (the same public `pk.` token as the web's `VITE_MAPBOX_TOKEN`) or the map renders blank; without `EXPO_PUBLIC_SUPABASE_URL`/`EXPO_PUBLIC_SUPABASE_ANON_KEY` the app shows mock spots and sign-in won't work. `mobile/build/` (local build output) is gitignored.

**Check-in prompts** (`mobile/src/lib/checkIns/`): opt-in (Settings → `src/app/check-ins.tsx` explainer, which asks for location, then "Always", then notifications). The OS geofences the 20 nearest spots (iOS's limit, used on both platforms; 100 m radius); `task.ts` schedules a local notification `PROMPT_DELAY_SECONDS` (5 min; `EXPO_PUBLIC_CHECK_IN_DELAY_SECONDS` overrides it for testing) after entering one and cancels it on exit. `rules.ts` holds the limits (3 h per spot, shared by spots within 200 m so one visit to a building gives one prompt; 3/day; quiet hours 10 PM–8 AM; skip closed spots). Geofence events are handled one at a time (`task.ts` queue) and every prompt reuses one notification id, so overlapping circles never stack prompts; with several pending, the nearest spot (fresh position fix) wins. The watched set is re-picked only after the user moves `REPICK_DISTANCE_M` (400 m) from where it was last picked: re-registering makes the OS send an initial exit for every circle the user is outside, so re-picking on every exit loops. Each decision (skip reason, scheduled, re-pick) is logged as `[check-ins] …`. "Still counting down" is asked of the notification system (`isPromptScheduled`), not worked out from the delay, because Android's inexact alarms fire late. On Android, geofencing also needs Google Location Accuracy consent (the enable flow calls `enableNetworkProviderAsync`, which covers location mode but not that consent); a background app only sees entries when something on the phone is requesting location, so an idle emulator needs the app in front to test. Everything — cached spots, history, the pending prompt — stays in AsyncStorage on the device; only the report is uploaded. The geofence task is defined in the custom entry `mobile/index.ts` (it must load before the router, including headless launches). Notification buttons open the app, which submits with `source: 'prompt'` (needs `supabase/migrations/0003_report_source.sql`; manual reports don't send `source`, so they work without it). Android stops geofencing once the app is swiped away (platform limit); iOS relaunches it. The location foreground service is disabled on purpose (not needed for geofencing, and a Play policy burden).

Mobile styling uses a semantic type scale (`text-caption`/`footnote`/`body`/`headline`/`title`, defined in `mobile/tailwind.config.js`) instead of `text-xs`/`sm`/`base`, and shadows come from `mobile/src/lib/elevation.ts` (`boxShadow`, which renders on iOS and Android) rather than `elevation`. A spot's busy color is shared by its map pin, list-row icon, `BusyBadge` and `BusyPanel` (`BusyStatus.tsx`). The icon/splash PNGs in `mobile/assets` are generated art (white pin + check on violet). Mobile's brand color is violet, including the low busy tier (labels Empty / Busy / Packed); the web app still uses emerald and the older labels. Mobile only greys out reports older than 2 h (no 30 min–2 h fade). The Explore sheet starts closed; the list opens at half and drags to full, a spot's card sizes to fit, and `enableOverDrag` stays off because dragging past the top snap leaves the sheet ignoring touches on Android.

**Styling:** Tailwind v4 via the `@tailwindcss/vite` plugin (no separate Tailwind config file — config is CSS-based per Tailwind v4 conventions). Design tokens (background/surface colors, busy-score tier colors, etc.) are documented in `spotcheck_TASKS.md` and should be pulled from there rather than invented ad hoc — e.g. busy-score tiers are low (≤3, emerald) / moderate (4–7, amber) / high (≥8, rose), implemented in `LocationPin.tsx`'s `getBusyTier`.

**Build order (from PRD §5 / TASKS.md):** pages are built against mock data first, sprint by sprint, with Supabase integration deferred to the last sprint. When implementing a new sprint's checklist items, check `spotcheck_TASKS.md` for the current sprint's scope and the "Explicit Out of Scope" list before adding functionality beyond what's listed.
